# M2-S7.2a E2 DL-only load sweep: protocol revision 2, predictions and validation requirements

**Status.** Declared 2026-11-03, before any E2 simulation. Authorisation: decision of 2026-11-03 20:05, "E2 preparation only", items 1–7.

**Not authorised:** the four-run re-baseline (step 0), any E2 or E2H5 run, Stage 6, and any change to the accepted Simu5G library. Each needs a separate decision. This file is not revised after any result. A correction is a new, dated revision, and the earlier text is kept.

**Supersedes** the design draft `results/M2-S7.2a-e2-protocol-draft.md` (revision 1, unchanged). The changes from it are listed in §9.

**Closed investigation (decision 2026-11-03 20:05).** The Q-d uplink investigation is closed with this conclusion: "Upstream Simu5G 1.8.0 grant-accounting defect; causal mechanism supported by an isolated single-UE counterfactual. The candidate fix is not adopted into the accepted simulation baseline."

**Strict shared-TTI Q8 exclusion rule (E1–E5).** Accepted, with fail-closed behaviour and the six controls preserved (`check_m2s72_e0.py`, `Q8(attr="exclusion")`).

## 1. Purpose and limits

**Purpose.** A matched DL-only comparison of Q-0 and Q-d, with **UL load factor 0 in both options**. It locates the DL saturation transition per N, placement and option, and the gPTP timing and reliability degradation around it.

**Cannot establish:**
- UL interference;
- UL-direction timing;
- bidirectional dependability;
- any statement about the UL-loaded regime.

The E0 UL-loaded results are unchanged. They are compared numerically only in the step-0 re-baseline (§4).

## 3. Implementation (Python only; done in this commit)

### Generator (`tools/m2s72_gen.py`)

**`load_spec` / `load_mixin` accept UL factor 0:**
- no talker load app, and `talker[k].numApps` = 3;
- the mixin name ends in `-u0`;
- a negative UL factor, or DL factor 0, is refused.

**Nominal DL factors (E2 only):**
- The interval 0.25 ms · n_loaded / F is rounded to the nearest ns.
- The generator refuses any factor whose effective value differs from nominal by more than **1e-5 (relative)**.
- The effective factor is written into the mixin description.
- The E0 path is still exact, and still refuses a non-integer interval.
- Example: F = 1.1 at one loaded UE gives 227,273 ns, an effective factor of 1.0999987.

**`e2_section` generates 196 configurations:**
- `M2S72-E2-<q0|qdu>-<one0|sym>-n<N>-f<F>`, 98 configs;
- `M2S72-E2H5-…`, 98 configs;
- their 98 `-u0` load mixins.

`m2s72.ini` changes only by additions. The single removed line is the generator-sha header line (`regen.txt`).

**`verify_e2`** checks all 196 configurations on OMNeT++'s own resolution (`opp_run -q runconfig`):
- every DL load value is the first match of its parameter path;
- no foreign app setting reaches a load app;
- **no UL load**: every `talker[k].numApps` = 3, and no entry can configure a `talker[k].app[3]`;
- HARQ16 on the gNB and every UE (E2), or no HARQ setting at all (E2H5);
- listener MAC, `numUe`, and a complete MAC log;
- each E2 / E2H5 pair differs only by the HARQ16 entries.

**Tests (`check/test_m2s72_gen.py`).** 18 new cases; 67 / 67 PASS in total. They include:
- UL factor < 0;
- DL factor 0 with UL factor 0;
- the exact path still refusing 1.1;
- the nominal refusal beyond 1e-5 (factor 11);
- the u0 spec and name;
- every E2 factor within tolerance (98 unique names, no sym at N = 1);
- `verify_e2_entries` passing as generated (HARQ16, HARQ5, sym n8);
- `verify_e2_entries` detecting each of: a talker UL app, a `talker[k].app[3]` entry, a wildcard talker app entry, a 1-ns-shifted DL interval, HARQ16 in an E2H5 config, HARQ16 missing on one UE, and the MAC log missing.

The unmodified sources regenerate the committed `m2s72.ini` byte for byte.

### Checker (`check/check_m2s72_e2.py`)

**`run` mode** — rows for every E2 run:

| Row | Content |
|---|---|
| **CFG-ident** | The `.sca` records exactly the generated `extends` list |
| **CFG-rate-DL** | The listener-egress load-frame timestamps are exactly the configured streams: one per loaded UE, from 0.3005 s, nominal-rounded ns interval, exact ps (a multiset). Each load app's source count equals its stream length, and the sum equals the egress count |
| **NO-UL** | <ul><li>effective `talker[k].numApps` = 3, from the recorded configuration;</li><li>no entry can address a `talker[k].app[3]`;</li><li>no `talker[k].app[3]` statistic;</li><li>0 load frames at every talker egress and at the listener ingress</li></ul> |
| **DL-active (info)** | The DL deactivation diagnostic (below) |

Missing evidence makes a row FAIL.

**`rebaseline` mode** — the step-0 acceptance checkpoint (§4).

**`controls` mode** — the row controls (§6).

### DL deactivation diagnostic (`check/diag_m2s72_dl_active.py`)

**What it does.** Per DL connection (gNB RLC UM TX entity, lcid = DRB), it replays the RLC TX queue and counts three things:
- **backlogged TTIs**;
- TTIs in which the scheduler lists the connection as a **candidate**;
- **DEACTIVATED** TTIs: backlogged, but not a candidate.

DEACTIVATED is split by whether an SDU arrived in the previous ms, and by whether the connection's last grant was capped.

**Status.** Observation only. It is never a gate, and it is never read as loss.

**Validation:**
- Self-test PASS: one candidate removed in memory is reported as exactly one DEACTIVATED TTI.
- On E0 Q-0 / Q-d at F = 1 and 2: 0 DEACTIVATED on every DRB (`dl-active-e0.txt`).
- E0 Q-d F = 2 makes 11,020 capped DL grants on DRB 1 without a deactivation, because an arrival in every TTI re-activates the connection.

### Runner (`m2s72.sh e2rb`)

**Refuses to start:**
- without `M2S72_E2_AUTH` (tested);
- with a Simu5G root other than `/root/stack/simu5g-1.8.0` (tested, using the candidate build);
- with a different library hash;
- with an existing `results/M2-S7.2a-e2rb`.

**What it then does:**
1. regeneration and verification;
2. the four runs, one at a time, with the E0 stop conditions:
   - free space ≥ 20 GB at start and ≥ 10 GB before each run;
   - run time ≤ 3 × estimate;
   - a simulator error stops the batch;
3. hashes;
4. `check_m2s72_e2.py rebaseline`.

## 4. Step 0: the DL-only re-baseline is an explicit acceptance checkpoint

**Runs.** `M2S72-E2-q0-one0-n1-f1`, `M2S72-E2-qdu-one0-n1-f1`, `M2S72-E2-q0-one0-n1-f2`, `M2S72-E2-qdu-one0-n1-f2` (seed 0, HARQ16, MAC log). At N = 1, F = 1 and 2 are exact, so the DL load spec is identical to E0's. This was verified by control PC-rate-e0-f1/f2.

**Acceptance rows** (all must PASS for all four runs):

| Row | Criterion |
|---|---|
| **RB-1** | Every E0 run-level gate under the E0 protocol §3 scoping. F0-1 is gated at F = 1, as in E0. Q8 must have 0 UNEXPLAINED. E0's UL-loaded CFG-rate is replaced by CFG-rate-DL and NO-UL |
| **RB-2** | CFG-ident, CFG-rate-DL and NO-UL PASS |
| **RB-3** | Achieved DL RLC-SDU throughput over [2 s, 12 s) is within **1 % (relative)** of E0 for the same option and factor (Q-0 f1 45.4445, Q-d f1 45.4445, Q-0 f2 54.9779, Q-d f2 54.5223 Mb/s; `results/M2-S7.2a-e0r2/e0-metrics.csv`). At F = 1, achieved ≥ 0.99 × offered |

Also required at run time: regeneration check, `verify` and generator tests all rc 0.

**Outcome:**
- **ACCEPTED** only if every row passes. Then the sweep (step 1) may be **proposed**, not run, and the multi-UE evaluator (§5) must be committed first.

A failed row is not reclassified, and the criteria are not revised.

## 5. Steps after an accepted step 0 (each needs its own authorisation)

### Step 1 — coarse bracket

Per (option, placement, N), 14 combinations: factors in ascending order from 0.8. Stop after the first factor that is overloaded by evidence (sustained growth on the load DRB **and** achieved DL < offered DL), plus one factor above it.

**N = 1:**
- The step-0 runs are the f1 and f2 points; they are not rerun.
- The N = 1 E0 capacity (≈ 1.21 × L_tot) is an expectation only. It is never used as a threshold for N > 1.

**Evaluator still required before step 1** (not done; Python only, with its own controls). It must extend the E0 run-level evaluation to N > 1:
- per-UE Q8 with the strict exclusion rule;
- per-UE capacity and backlog;
- I-5 / AR for one0 against N = 1;
- M3 / M3d at N ≥ 2;
- I-4 stream at N = 2 and 4.

The step-0 checkpoint covers N = 1 only.

### Step 3 — HARQ5 pairing

One E2H5 run per combination, at the last non-overloaded factor, evaluated with the strict rule. An unattributable deletion is a stop condition. All 98 E2H5 configurations are generated because that factor is not known in advance.

### Removed from this protocol

Bisection between grid factors (draft step 2) and seed replication are removed. Their configurations do not exist: the seeds are fixed per configuration, and bisection factors depend on results. Adding them requires a generator revision, exact verification and a new declaration.

### Q-d DL deactivation at N > 1 (hypothesis H-DL-403, declared now)

**Mechanism.** The `:403` defect can deactivate a backlogged DL connection when no SDU arrives before the next TTI. This is possible only when the per-UE DL interval exceeds 1 ms: sym at N = 4 for F < 1, and sym at N = 8 for F < 2.

**Prediction.** DEACTIVATED > 0 (without arrival, after a capped grant) can appear only in Q-d runs of those combinations once their load DRB is backlogged. It never appears in Q-0, which is uncapped.

**Interpretation rule (fixed now).** Any Q-d run with DEACTIVATED > 0 is labelled "Simu5G :403-affected". Its capacity and timing values are reported, but they are not interpreted as QoS-scheduler behaviour.

### Other reporting

Thresholds, onset and per-N reporting are as in draft §4, unchanged.

### Estimates

Estimates are scaled from E0 at N = 1 (wall 105–193 s at F = 1–2; raw 0.41–0.88 GB with UL load). Multi-UE scaling is unmeasured, so the estimates are declared conservatively:

- **Raw per run:** 0.9 · (1 + 0.5 (N − 1)) GB, i.e. 0.9 / 1.35 / 2.25 / 4.05 GB at N = 1 / 2 / 4 / 8.

### Storage constraint (measured 2026-11-03)

**11 GB free** on the 252 GB volume.

| Item | Size |
|---|---|

The runner's start rule (≥ 20 GB free) **will refuse step 0 as things stand**. Two decisions are required, and nothing has been deleted:

**D-S1, before step 0: free ≥ 9 GB.** Options:
- (a) delete the E0 raw outputs. Their 333 hashes and all derived records are committed, but re-checking E0 would then need a rerun;
- (b) delete the candidate-build raw outputs (74 hashes committed) plus other dispensable raw outputs. Probably insufficient on its own;
- (c) provide more disk.

**D-S2, before step 1: a per-run raw-retention rule.** The step-1 maximum does not fit the disk. Candidate rule:
- keep raw outputs until the run's check and hash manifest are written;
- then keep `.sca` / `.vec` / `.vci`, the gzip MAC log and the derived rows (≈ 80 MB per run, measured on E0 `q0-f2`);
- delete PCAP, CSV logs and eventlog.

Alternatively, compress them.
