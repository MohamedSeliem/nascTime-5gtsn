## Verdict: FAIL — stop and report

| | Result |
|---|---|
| Gate rows (90 runs, 18 configs x 5 seeds) | **1770 PASS, 0 FAIL** |
| Negative controls (each must fail exactly its predicted row families) | **2 PASS, 4 FAIL** |
| Checkpoint 2 | **FAIL** |

**Why it fails.** All the gate rows pass. But four of the six negative controls did not fail exactly the row families predicted for them before the runs. Under the standing rule, a control whose result differs from its prediction is a failing control. It is not reclassified. The predictions are therefore left unchanged. Section 5 gives the mechanism for each mismatch. Section 8 proposes corrected controls, which need approval before they are used.

**Evaluation limits (section 4).** Independently of the controls, the Block B runs barely exercise two parts of the cross-slave requirements:
- **Case B (different-Sync samples):** 17 of 2,492,630 used samples, all in q0-ideal.
- **Path-specific differences in residence, slave reception or update instants:** these occur only in q0-ideal. That is the one configuration where such differences produce no clock-error difference.

So in these runs, every cross-slave difference comes from the per-DS-TT TT clocks (E-all). The M4 GM-drift pair attribution was evaluated only where Res_i = Res_j. These requirements PASS as rows, but the evidence for them is weak, and it is reported as such.

**M4 detail.**
- **GM drift:**
  - over every residence interval of every slave, the GM rate (O1, unquantized) is one value: ρ_G = 1 + 100 ppm + 4.545e-20 (the exact rate of the 1 ns-tick oscillator in double arithmetic);
  - the rate part of E_res = (r − ρ_G)·Res for every slave Follow_Up;
  - per pair and common Sync, the difference = (r − ρ_G)(Res_i − Res_j).
- **TT clocks (Eall):**
  - the T rows hold with each DS-TT's own D-13 parameters;
  - Rr.TT_nw is identical across slaves;
  - Rr.TT_ds,i − Rr.TT_ds,j = r·[Δθ0 + Δosc + Δw + Δq] exactly, with Δθ0 = 100 ns·(i − j). The θ0 part at the last Sync for pair (0,1) is −100.01 ns, i.e. r × 100 ns.
- **At N = 1** the pair part is not applicable and is reported as such (section 7, fix 1).

## 4. Requirements failed, unevaluated, or evaluated only weakly

**Failed:**
- Negative controls NC-swap, NC-cancel (qG2), NC-cfout and NC-tse (section 5).

**Unevaluated:**
- **I-4, DS-TT 1 own noise stream at N = 2 vs N = 4.** Stated in the checker docstring, not implemented in the row. A supplementary diagnostic is in section 6; it is not a gate.

**Weakly evaluated (rows PASS, evidence thin):**
- **M3d case B.** 17 samples in total, all q0-ideal, where every term is identical anyway. The case-B branch ("full term-by-term difference sums exactly") has effectively not been exercised with non-zero differences.
- **Path-specific instants.** The supplementary diagnostic (section 6) counts the Follow_Ups whose s_e, s2, s_F or Res differ between slaves:
  - q0-ideal: non-zero (9–12 of 95 per seed at N = 2, 19–22 at N = 4);
  - all Ca, Eall and qdu runs: 0 (see `diag-cp2.txt`).

  So, in the runs where clocks are non-ideal, every slave has the same egress, reception and update instants.
- **M4 GM drift, pair part.** Evaluated only with Res_i = Res_j, so the identity reduces to 0 = 0. The single-slave part, rate part = (r − ρ_G)·Res, is evaluated non-trivially on every Follow_Up.
- **Path-specific categories of M3d (d).** "Residence" (beyond per-path rounding), "slave link" (beyond TT-induced Pdelay differences) and "GM quantization at s2" were never non-zero. Every cross-slave difference in this record is caused by the per-DS-TT TT clocks.
- **Consequence.** The cross-slave claims of Stage 4 are demonstrated for **TT-clock heterogeneity with identical 5G paths**. They are **not** demonstrated for heterogeneous 5G paths with drifting clocks. Idle Block B does not produce that condition; whether loaded configurations do is for review (section 8), not for this record.

## 5. Negative controls

The predictions were fixed before the trial run and are unchanged.

| Control | Predicted to fail | Failed | Result |
|---|---|---|---|
| NC-swap: B-q0-Eall-n4 seed 0, slave 1 analysed with DS-TT 2's logs, frames and TT log | M2, M3 | M2, M3, **M3d, M4** | **FAIL** |
| NC-theta1: `M2S72-BN-theta1` (DS-TT 1 θ0 + 1 µs), checker uses D-13 | M2, M4 | M2, M4 | PASS |
| NC-cancel: Rr.mul claimed cancelling | M3d | M3d (10,870 case A samples per pair, first at 1.13 s) | PASS |
| NC-cancel: qG2 claimed cancelling | M3d | **none** | **FAIL** |
| NC-cfout: copy with DS-TT 1's logged cfOut + 1 ps on one Follow_Up | I-3, M2, M3 | M2, **M3d** (I-3, M3 not failed) | **FAIL** |
| NC-tse: copy with DS-TT 1's logged TSe + 1 ps on one Follow_Up | I-1, M2, M4 | I-1, M2, M4, **M3d** | **FAIL** |

**Mechanisms (from the run evidence and the code):**

1. **NC-swap, extra M3d.** M3d (c) is implemented as "Σ path-specific (x_i − x_j) = **measured** D_ij".
   - With swapped evidence, the terms describe the swapped prediction, which differs from the measurement (M3 fails on 11,870 of 11,870 samples). So (c) fails.
   - Design 4.2.3 (c) writes "= D_ij(t)", and 4.2.2 defines D_ij = e_i − e_j. This does not say whether D_ij is the measured or the predicted value. I kept the stricter reading, measured, and did not change it after seeing the result.
   - Under the predicted reading, (c) would hold here and M3 alone would catch the swap.

   **NC-swap, extra M4.** The M4 TT row includes the per-slave T rows ("TT stamps recomputed with DS-TT k's own D-13 parameters"). Slave 1 analysed with DS-TT 2's TT log fails them, and the pair TT identity fails for 285 of 570 Sync-pairs. The prediction omitted M4 although M4, as defined, uses that evidence: this is a prediction error.

2. **NC-cancel (qG2): premise false in Block B.** qG2 = G(s2) − C_G(s2) is path-specific only if the slaves' s2 differ. In B-q0-Eall-n4, s2 is identical for all four slaves for 95 of 95 Follow_Ups (`diag-cp2.txt`), so qG2 is in fact bit-identical. A cancellation claim that is true in the data cannot be detected as false.

3. **NC-cfout.**
   - **I-3 not failed:** +1 ps is below the wire resolution. INET `writeClock8` drops the sub-ns part (`inet_model.inet_write_clock8`, :106–112), so writeClock8(cfOut + 1 ps) equals the wire value.
   - **M3 not failed:** M3 compares the recorded clocks with the O5/O1 prediction. O5 does consume the logged cfOut (`check_m2s5.cf_map` → `check_m2s6.Eval` :190–193). The +1 ps changed the predicted gmRR (1.0002000710951096 → 1.0002000711031103), and the M2 S row caught this against the recorded slave value. But the resulting change in the predicted slave clock at the 1 ms samples is below the slave's 1 ns clock tick, so the predicted and measured e_i − e_j are unchanged.
   - **M3d failed** on the per-slave identity e = Σ terms (125 samples per pair with slave 1): the terms carry the exact +1 ps, while the clock prediction is quantized to 1 ns.

4. **NC-tse, extra M3d.** Same per-slave identity mechanism as NC-cfout (125 samples per pair with slave 1). The prediction omitted it.

**Disclosure on NC-theta1.** This control also mismatched in the trial run (failed F0-1, F0-5, M2, M4). The cause was a checker bug, `opt_of("M2S72-BN-theta1")` → "qdu" (fix 2, section 7). It passes only after that fix.

## 7. Development history and checker fixes

**Trial run.** A full Block B trial (`b`) was made with the uncommitted Stage 4 code. It is kept locally in `results/M2-S7.2a-cp2-trial1/` (gitignored); its check output is committed as `results/M2-S7.2a-cp2-trial1-b-check.txt`.
- **Raw outputs:** trial and clean record are byte-identical (5,472 files, identical sha256 lists).
- **Trial gate result:** 1760 PASS, 10 FAIL.

**Fixes made after the trial, before the clean record (commit `ae2857c`):**

1. **M4 TT row at N = 1.** The row required `n_tt > 0` pair comparisons, which N = 1 cannot have: all 10 trial failures were Eall-n1. The pair part is now "not applicable" at N = 1; the T rows (per slave) must still be present and pass. Nothing changed for N ≥ 2.
2. **`opt_of` for `M2S72-BN-theta1`.** The config was read as qdu instead of q0, which failed the control's F0-1/F0-5. It now maps through `BN_BASE` to `M2S72-B-q0-Eall-n4`, and an unknown option raises an error.

**Fixes during development, before the trial:**
- the `reads0` snapshot of the GM reads (KeyError);
- I-1 log semantics: the syncTx row logs simulation time, the corrected row logs the TT stamp;
- M4 ρ_G: the exact 1 + 100 ppm assumption was wrong by 4.5e-20. M4 now requires one constant value and reports its offset.

**Not changed after the trial:**
- M3d (c) (measured reference);
- every control prediction;
- every acceptance criterion.

The only effect of the two post-trial fixes on the gate outcome is the 10 M4 N = 1 rows (FAIL → PASS) and NC-theta1 (FAIL → PASS).

## 8. Proposed corrections, for approval and not applied

1. **NC-swap.** Rule on M3d (c): measured or predicted D_ij. With measured, as now, predict {M2, M3, M3d, M4}. With predicted, predict {M2, M3, M4}. In both cases M4 belongs in the prediction.
2. **NC-cancel (qG2).** Replace it with a claim that is false in the data: Rr.TT_ds (or D.TT) claimed cancelling, on B-q0-Eall-n4 seed 0, predicted {M3d}. Alternatively, keep qG2 but evaluate it only on a run where s2 differs between slaves with a non-ideal GM. No Block B run provides that.
3. **NC-cfout.** Use a mutation at or above the wire resolution (+1 ns on the logged cfOut), with predictions fixed before the run. I-3 is expected to fail (the wire value differs), and M2 and M3d on the identity. Whether M3 fails depends on whether the prediction change crosses a slave clock tick at a 1 ms sample; that must be predicted a priori or M3 left out. Optionally, add a second control that mutates the wire cf of one received Follow_Up (pcap copy) to exercise I-3 directly.
4. **NC-tse.** Predict {I-1, M2, M3d, M4}.
5. **I-4.** Implement the DS-TT 1 own-stream check as a gate row (comparison as in diagnostic 2).
6. **Path heterogeneity.** Decide whether Stage 4 needs evidence with differing 5G paths and drifting clocks (e.g. a Block B variant under load). Without it, M3d case B and the M4 pair part stay weakly evaluated. Such a variant would be a new config inside Stage 4, not Stage 5 scaling. Whether it is in scope is for review.
