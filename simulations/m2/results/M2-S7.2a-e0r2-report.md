### A.5 Can the P1 five-HARQ run validate Q8 on real deletions? (read-only feasibility, not a gate)

Q8 was applied to UE 1 of the existing P1 run `M2S72-H-q0-Ca-n2` (HARQ 5, N = 2), with its P1 observation-twin MAC log. Output: `results/M2-S7.2a-e0r2/p1-feasibility.txt`.

- P1 established the twin as non-perturbing.
- Q8-x passes on this pair: RLC TX / RX log counts equal the vectors, and there is no UNCLASSIFIED line.

**What Q8 finds.**
- The replay predicts all 37,308 observed UE 1 deliveries.
- 40 UE-1 gPTP frames are undelivered, the same 40 as P1's ledger. P1 counts 39 as being in deleted MAC PDUs and 1 without a discard. Q8 classes 38 as destroyed and 2 (S95, F95) as censored: their last RLC PDU went out at 11,999 / 12,000 ms, so delivery was due after T_end and the reception window was still open. F95's TTI is a deletion TTI in P1's ledger; Q8's censoring takes precedence there, which is the conservative choice.
- **5** frames are attributed to an observed HARQ-process deletion: F6, F7, F18, F83, F89.
- **33** frames are UNEXPLAINED, so Q8 FAILS on this run. Their deletion TTIs (Sync instants: 750, 1500, … ms) also carried gNB RLC PDUs of UE 0, because both UEs receive their Sync copy in the same TTI. The MAC log's deletion line (`LteMacEnb.cc:585`) carries **no UE identity**, so under the strict N > 1 attribution rule a deletion there is not attributable.
- 1,213 load SDUs are destroyed without an attributable discard, for the same reason.

**Conclusion.** Validating Q8 on real simulator deletions is **feasible but not complete** with the existing evidence.

- **Evidence missing:** the identity of the UE whose MAC PDU was deleted in a TTI shared by several UEs.
- **Ways to obtain it without inventing observations** (none implemented, decision needed):
  - **(a)** A declared exclusion rule: if every RLC PDU of every other UE in that TTI was received, the single deleted MAC PDU must be UE k's (one MAC PDU per UE per TTI). This is packet-level and evidence-based, but it is a new attribution rule.
  - **(b)** P1's macPduMake-block mapping (computeTxParams order). This is a log-structure heuristic, so weaker evidence.
  - **(c)** A capture that carries the UE id on the deletion line. That needs a C++ or upstream log change, which is not authorised.
- **Why it matters beyond P1:** E1 / E2 HARQ5 runs at N > 1 have the same limitation. As implemented, Q8 would correctly report such losses as UNEXPLAINED (fail closed) rather than attribute them.

## Part B — Q-d uplink starvation: root-cause localisation (read-only)

**Inputs.**
- Existing E0 outputs: `M2S72-E0-q0-f1` vs `M2S72-E0-qdu-f1` (N = 1, HARQ16), checked again at factor 8.
- UE and gNB RLC vectors and the gNB MAC log.
- The Simu5G source of the tree used (`/root/stack/simu5g-1.8.0`).
- Diagnostic: `check/diag_m2s72_qd_ul.py`. Outputs: `qd-ul-f1.txt`, `qd-ul-f8.txt`.

### B.1 Observations, time-aligned, window [2 s, 12 s)

| Stage (path order) | Q-0 (MAXCI) | Q-d (QOS_PF) |
|---|---|---|
| UL offered at UE RLC UM TX (DRB 1, LCG 3), SDUs / bytes | 40,500 / 56.86 MB | 40,500 / 56.86 MB (**identical: admission is not the cause**) |
| RAC (scheduling request) successes | 97 | 435 |
| BSR reports received (UlBacklogRegistry, LCG pseudo-connection lcid 67) | 97 | 434 |
| TTIs in which lcid 67 is a scheduling candidate | 7,866 | **434** |
| TTIs with a UL grant / granted bytes | 7,866 / 57.01 MB | **434 / 3.15 MB** |
| UE RLC PDUs sent (MAC requests) | 48,456 | 3,105 |
| UL SDUs delivered by the gNB RLC | 40,510 | 2,243 |

**Per BSR cycle.**
- **Q-0:** grants continue every TTI until the reported bytes are served, then stop until the next BSR.
  - Cycle 1: BSR at 109 ms reports 25,541 B; 4 grants give 25,557 B = 25,541 + 4 × (MAC 2 + RLC 2 B).
  - Later cycles are 103 TTIs, of which 81 have grants. The UE sends a new BSR only about every 100 ms, and each one reports its whole queue.
- **Q-d:** every one of the 434 cycles has **exactly one** grant. Each grant is **granted = limit = 7,250 B**, the whole cell. That is followed by 22 TTIs in which lcid 67 is not a candidate, then a new RAC → BSR. The cycle is exactly 23 TTIs.
  - Check: 434 × 7,250 B × 8 / 10 s = 2.52 Mb/s, against 2.48 Mb/s observed at the listener.

**First divergence.**
- Both options receive the same first BSR at **109 ms** (25,541 B).
- **At 110 ms** Q-0 schedules lcid 67 again (and at 111 and 112 ms). Q-d does not: lcid 67 is no longer in the UL active set.
- Everything before that is identical: UL admission, the first RAC (103 ms), the first BSR.

**DL is not the cause.** Every UL count is identical at factor 1 and factor 8 in both options (`qd-ul-f8.txt`). UL resources are not the constraint: in each of the 434 Q-d scheduling TTIs all 50 UL RBs were free before the grant (`computeTotalRbs UL - total 50, allocated 0`). In the other 9,566 TTIs no UL connection was a candidate at all, and at N = 1 no other user or flow could hold UL RBs.

### B.2 Mechanism (source reading; consistent with every number above; not tested by a counterfactual run)

**The code path.** `LteSchedulerEnb::scheduleGrant`, `stack/mac/scheduler/LteSchedulerEnb.cc:402–408`, updates per band:

```
toServe     = (uBytes > toServe) ? 0 : toServe - uBytes;
queueLength = (uBytes > toServe) ? 0 : queueLength - uBytes;   // compares with the UPDATED toServe
if (toServe == 0) { stop = true; if (queueLength == 0) active = false; break; }
```

**Q-d (QoSAwareScheduler):**
1. It passes a byte cap, `limit = quota` (= 7,250 B for a single UE).
2. In the band that exhausts the cap, `toServe` becomes 0.
3. Line 403 then compares `uBytes > 0`, sets `queueLength` to 0 although the reported backlog (≥ 18 kB at the first cycle, 15.6 MB by 3 s) is not served, and line 408 sets `active = false`.
4. QoSAwareScheduler Phase 3 erases an inactive CID from the active sets (`QoSAwareScheduler.cc`, `if (!active)`), and `commitSchedule` copies that set back to the eNB scheduler.
5. In UL the only path that re-activates the LCG connection is the `UlBacklogRegistry` backlog callback, which fires on a **new BSR**. So the UE gets one grant per SR / RAC → BSR cycle (23 TTIs).

**Q-0 (LteMaxCI)** passes an unlimited cap (`4294967295U`), so `toServe` equals the queue and reaches 0 only when the queue is actually drained. `active = false` is then correct.

**In DL, Q-d is not starved.** The same deactivation is undone every TTI, because every new DL RLC SDU calls `backlog(cid)` (`LteMacEnb.cc:760`). DL candidate TTIs: 10,581 in 10,000 TTIs. A DL connection that holds a backlog but receives no new SDUs would be exposed to the same effect. That was not observed in E0, and it is a hypothesis for later runs.

**Classification.**

| Possible cause | Assessment |
|---|---|
| Resource constraint | Not one: UL RBs are idle |
| Configuration | Not a misconfiguration in the sense of wrong parameters. The Q-d configuration selects QOS_PF for UL (`schedulingDisciplineUl = "QOS_PF"`), and that is what exposes the defect |
| Implementation | The observed starvation is explained by an **implementation defect in the shared grant-accounting path** of the Simu5G tree used here. It is triggered by capped grants, which only the QoS-aware scheduler issues in these configurations |

The 23-TTI SR / RAC → BSR period itself comes from UE-side timers, which this log does not capture (no UE MAC log). That part is a hypothesis.

**Not established.**
- Whether this line is identical in upstream Simu5G 1.8.0. The upstream source could not be fetched from this session, so the tree used is the reference.
- Whether correcting line 403 (for example, comparing with the pre-update `toServe`) removes the starvation. That needs a code change and a run, neither authorised.

**Not changed.** The Simu5G source, the scheduler configuration, any run.

**Implications.**
- Q-d's UL load and any UL-dependent metric (UL residence, cross-UE UL interference, listener-side UL counts) are not interpretable in E1 / E2 until this is resolved or explicitly scoped out.
- DL gPTP results of Q-d in E0 are not affected: DL candidates are present every TTI.
- This touches the QoS-PF scheduler code path. It should be raised in the Simu5G contribution plan as a candidate issue with this evidence, not as a confirmed upstream bug.

## Part C — Revised E2 design recommendation (not run)

**Principle.** Locate and characterise the saturation transition per N from measured evidence (sustained growth on the load DRB together with achieved < offered, protocol §1). Never import the N = 1 value (≈ 1.21 × L_tot DL, Q-0) into N > 1.

**Stage C1 — coarse bracket, per N ∈ {1, 2, 4, 8}.**
- Placement: sym and one0.
- Options: Q-0 and Q-d. For Q-d, report DL only, and keep UL at 1 × until Part B is resolved; otherwise declare its UL as out of scope.
- HARQ16, seed 0.
- Candidate factors: **0.8, 1.0, 1.1, 1.2, 1.3, 1.5, 2.0 × L_tot**. Run in ascending order. Stop at the first factor showing overload by evidence, plus one factor above it for confirmation. At N = 1 that predicts 1.0 → 1.1 → 1.2 → **1.3** (first overload; 1.21 measured) → 1.5, so 5 runs per (option, placement).
- Bound: ≤ 7 runs per (N, option, placement), typically 4–5. The 2.0 factor is only needed if 1.5 is not yet overloaded.

**Stage C2 — refinement and replication, at the bracket of each N.**
- Bisect the factor interval [last non-overloaded, first overloaded] once or twice (e.g. 1.2 → 1.25 → 1.225). The generator accepts any factor whose interval is an exact number of ns, and refuses others (fail closed).
- Replicate the two factors around the transition at seeds 0–2.

**Stage C3 — HARQ5 pairing** (Simu5G-specific, experimental): one HARQ5 run at each N's last non-overloaded factor, seed 0.
- This needs the Part A.5 attribution decision first. Otherwise Q8 would correctly mark the N > 1 HARQ5 losses UNEXPLAINED and stop the batch.

**Estimated size.** About 4 N × 2 options × 2 placements × 5 (C1) + about 4 × 2 × 2 × (2 + 4) (C2) + 16 (C3), i.e. **≈ 270 runs at most**, of which about 160 in C1. This is driven down by the stop rule. N = 8 sym runs are the largest; the measured E0 sizes give ≤ 2.2 GB per run at 8× offered load.

**Per-batch decisions to declare in advance:**
- the loss-free set (F0-1) = factors below the measured transition of that N, from C1 evidence only;
- censoring reported at horizon 12 s, as rates;
- the onset thresholds as in protocol §5, with sensitivity.

**Prerequisites before any E2 run:**
1. Part B decision: Q-d UL scoped out, or corrected and re-baselined. A correction is out of scope here.
2. Part A.5 decision: the N > 1 deletion attribution rule.
3. A new protocol and predictions commit.
