### A.1 Hypothesis

`LteSchedulerEnb::scheduleGrant`, per band (`:402–408`):

```
toServe     = (uBytes > toServe) ? 0 : toServe - uBytes;
queueLength = (uBytes > toServe) ? 0 : queueLength - uBytes;
if (toServe == 0) { stop = true; if (queueLength == 0) active = false; break; }
```

**How the defect marks a backlogged connection inactive.** Line 403 compares `uBytes` with the **already decremented** `toServe`.
1. In the band where a **capped** grant (`bytes` < backlog) is exhausted, `toServe` becomes 0.
2. Then `uBytes > 0` holds, so `queueLength` is set to 0 although backlog remains (`queueLength_before − uBytes` > 0).
3. Line 408 then sets `active = false`.
4. QoSAwareScheduler (Phase 3, `if (!active)`) removes the CID from its active sets, and `commitSchedule` writes that set back to the eNB scheduler.
5. In UL the CID returns only when the `UlBacklogRegistry` callback fires on the next BSR.

**When it matters.**
- LteMaxCI passes `bytes = 4294967295`, so `toServe` = `queueLength`. Both counters fall by the same `uBytes`, and when `toServe` reaches 0 the queue really is empty. `active` is the same as under the corrected line in every single-codeword grant.
- E0 logs show one codeword per grant ("on 1 codewords"), so the multi-codeword path is not exercised.

### A.2 Candidate fix (minimal; `results/M2-S7.2a-cfqd-candidate-fix.patch`)

```
-            queueLength = (uBytes > toServe) ? 0 : queueLength - uBytes;
+            queueLength = (uBytes > queueLength) ? 0 : queueLength - uBytes;
```

The new value is the pre-grant backlog minus the booked bytes, floored at 0.

**Affected scheduler state:** only `queueLength` inside `scheduleGrant`, and through it `active` (`:408`) and the next codeword's `queueLength` / `toServe` (`:314–315`, multi-codeword only).

**Unchanged:**
- `toServe`;
- band booking;
- the virtual-buffer and mirror drains (`:476–496`, which do not read `queueLength`);
- quotas, scores and every other module.

**Build.** An isolated copy at `/root/cf/simu5g-1.8.0-qdcf` (`cp -a` of the accepted tree, the one line changed, incremental `make MODE=release`). Its `libsimu5g.so` sha256 is `87f45b9b…`.

**Runner guards (`m2s72.sh cfqd`).** The runner refuses:
- the accepted path;
- any source difference other than this patch.

**Linking.** nascTime's `libnasctime_m2.so` has no Simu5G dependency and is not rebuilt against the copy.

## Part B — strict shared-TTI attribution rule (Q8, N > 1, opt-in; `check_m2s72_e0.Q8(attr="exclusion")`)

### B.1 Rule

A deletion in TTI t is attributed to UE k's missing PDU only if all of the following hold:

| # | Condition |
|---|---|
| E1 | The MAC log gives the TTI's DL MAC PDU count n and deleted count d ≥ 1 |
| E2 | Candidate set = the UEs with gNB RLC PDUs (any DRB, entity `rlc-um-<node>-<drb>`) sent in t, one MAC PDU each: \|candidates\| = n |
| E3 | Every candidate PDU's reception window is closed by T_end |
| E4 | Per candidate, its PDUs of t are all received (positively not deleted) or all missing (a deleted MAC PDU loses all of its content). Partly received means inconsistent, so the deletion is not attributable |
| E5 | The all-missing candidates are exactly d, and UE k is among them. That assignment is then the only consistent one |
| E6 / E7 | No delivered SDU may own a missing PDU, and every SDU of the deleted PDU must be accounted for. These are the existing Q8 model rows ("delivered SDU with a PDU never received"; "destroyed SDUs without an observed discard") |

- Receptions are matched per entity with the existing greedy rule (same size, within AIR = 4 ms).
- **Logging order is not used.**
- Anything else stays UNEXPLAINED and fails Q8.
- **Scope.** At N = 1 the E0 rule is unchanged, and so is the default (`attr=None`), so the E0 / E0r2 evaluations are unaffected.

### B.2 Evaluation

`check_m2s72_e0.py attr`, on the existing P1 run `M2S72-H-q0-Ca-n2` UE 1 with its twin MAC log. Read-only, no simulation.

**Reported, not predicted:**
- how many of the 33 frames that are UNEXPLAINED under the revision-2 rule become uniquely attributable, and how many stay unresolved, each with its rule outcome;
- that no other fate changes;
- the Q8 row under the rule.

**If no frame becomes attributable**, the controls cannot be evaluated. The work stops with a recommendation for UE-ID instrumentation.

### B.3 Controls (on the first frame, in GM time order, that the rule attributes; mutations of the rule's inputs only)

| Control | Mutation | Predicted fate of that frame |
|---|---|---|
| PC-attr | none | lost, "HARQ-process MAC PDU deletion … (strict exclusion …)" |
| NC-attr-ambiguous | Every reception of the other UE's PDUs in that TTI removed, so two candidates are all-missing and d = 1 | UNEXPLAINED, by E5 |
| NC-attr-partial | One reception of the other UE's PDUs in that TTI removed | UNEXPLAINED, by E4 if the other UE has ≥ 2 PDUs in the TTI, else by E5 |
| NC-attr-count | The TTI's deletion removed (d = 0) | UNEXPLAINED, by E1 |
| NC-attr-received | One reception added for one of UE k's PDUs in that TTI | UNEXPLAINED, by E4 if UE k has ≥ 2 PDUs in the TTI, else by E5 |

The E4 / E5 alternative is fixed by the TTI's PDU counts, which are printed before evaluation. A control that does not produce its predicted fate and code fails, and is not reclassified.
