## The code

```cpp
// per band, after booking uBytes
toServe     = (uBytes > toServe) ? 0 : toServe - uBytes;
queueLength = (uBytes > toServe) ? 0 : queueLength - uBytes;   // compares with the ALREADY decremented toServe
if (toServe == 0) {
    stop = true;
    if (queueLength == 0)      // "the connection has also terminated the buffer"
        active = false;
    break;
}
```

**The defect.** When the grant is capped (`bytes` < backlog), `toServe` reaches 0 in the band that exhausts the cap. Line 403 then evaluates `uBytes > 0`, sets `queueLength = 0` while backlog remains, and line 408 reports `active = false`. A scheduler that honours `active` drops the connection from its active set.

**Who is affected.**
- In UL the connection only comes back through the backlog callback on the next BSR. So the UE gets **one transport block per SR / RAC → BSR cycle**.
- Uncapped callers (LteMaxCI passes `4294967295U`) are unaffected: there `toServe` = `queueLength`, so both reach 0 together.

## Minimal scenario and evidence

**Scenario.** One gNB, one NR UE, N = 1, 50 RB, CQI 15, 1 ms TTI, HARQ 16 processes. UL: 1400 B every 0.25 ms (44.8 Mb/s) on the default DRB (UM, LCG 3). `schedulingDisciplineUl = "QOS_PF"` vs `"MAXCI"`, otherwise identical, seed 0, 12 s. The scenario comes from nascTime's E0 configuration, and an equivalent upstream example still has to be written.

## Candidate correction (one line) and its isolated results

```diff
-            queueLength = (uBytes > toServe) ? 0 : queueLength - uBytes;
+            queueLength = (uBytes > queueLength) ? 0 : queueLength - uBytes;
```

The new value is the pre-grant backlog minus the booked bytes, floored at 0. Nothing else changes: not `toServe`, the band booking, the virtual-buffer or mirror drains, nor the quotas.

**Results on an isolated build** (v1.8.0 plus this line only):
- **QOS_PF UL** becomes identical to MAXCI in every UL counter (table above). Grant accounting: no cycle granted more than reported + headers. UL SDU and byte conservation is exact.
- **DL results under QOS_PF are unchanged.**
- **MAXCI regression:** with the fix, MAXCI reproduces 1.8.0 exactly in every PCAP, vector, scalar, MAC-log line and fingerprint (`1f14-1d51/tplx`), and in every eventlog event, message, module and log record.

## Limitations (not tested)

- **DRR.** `LteDrr` calls `requestGrant(cid, desc.deficit_, …)`, which is also a capped grant. It is likely affected, but this was not run.
- **Multi-codeword grants.** With the original line, the next codeword's `queueLength` may also be under-stated (`:314`). Only single-codeword grants were exercised.
- **DL with idle backlog.** In DL, every new SDU re-activates the connection (`LteMacEnb.cc:760`), which masks the defect while arrivals continue. A backlogged DL connection without new arrivals under a capped scheduler is untested.
- **Multi-UE.** Only N = 1 was tested. The quota split at N > 1 makes capped grants routine, so the effect is expected to be stronger. This is not measured.
- **Related path.** `scheduleGrantBackground` (`:733–738`) sets `active = false` whenever `toServe` reaches 0, which is a different code path. It was not examined.
- **Related report.** nascTime's earlier DL tail-cut finding (one RLC header counted per connection, `:314`; inactive when the booked queue reaches 0, `:403–408`) involves the same lines. It is a separate issue draft (U-2).
