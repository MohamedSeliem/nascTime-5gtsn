### 1.2 What fails: learning the listener's VID-42 entry

The UPF bridge is INET's `MacForwardingTable`, which learns **per (VLAN id, MAC)**: `RelayInterfaceLearner` calls `learnUnicastAddressForwardingInterface(interface, source, vid)`.

**Before 0.3 s the listener sends only untagged gPTP frames** (VID 0). So its VID-42 entry is created only by its first VLAN-42 data frame, which under D-4 is the first DL base frame:
- λ_L = 0.300002180000 s.

**The talkers' uplink base flows (VLAN 42, to the listener) start at 0.1 s:**
- the first one reaches the UPF at τ_L = 0.109000185200 s;
- every such frame up to 0.3 s is an unknown unicast, flooded to `dnEth` **and to every other session**.

| Run | F0-6 (listener, VID 42) | F0-4 misdirected frames M_j (all to the listener, first/last) |
|---|---|---|
| q0-n1, qdu-n1 | MISORDERED, margin −0.191001994800 s | 0 (one session: nowhere to flood) |
| q0-n2 | MISORDERED, −0.191001994800 s | [20, 20], 0.109000320400 s / 0.297000726000 s |
| q0-n4 | MISORDERED, −0.191001994800 s | [57, 59, 58, 57] (total 231), last 0.298000590800 s |
| q0-n8 | MISORDERED, −0.191001994800 s | [136, 136, 137, 136, 136, 137, 137, 137] (total 1092), last 0.300001131600 s |
| qdu-n2 | MISORDERED, −0.191001994800 s | [20, 20], last 0.297000726000 s |
| qdu-n4 | MISORDERED, −0.191001994800 s | [60, 60, 60, 60] (total 240), last 0.297003430000 s |
| qdu-n8 | MISORDERED, −0.191001994800 s | [135, 137, 137, 135, 135, 136, 135, 135] (total 1085), last 0.300001131600 s |

**The talker direction is VALID in every run:**
- λ_k = first uplink frame of `talker[k]`, at 0.109000185200 + k·0.000000135200 s (k = 0 … 7, N = 8);
- τ_k = first DL unicast, at 0.300002180000 + k·0.000001136 s;
- margin ≥ 0.191001994800 s, each learned on talker[k]'s own tunnel.

After λ_L, no frame is misdirected in any run.

### 1.3 What this means

- The rev. 2 design (3.3) assumed that MAC learning is not per VLAN and that "the expected flood count is zero" with the 0.3 s DL start. **That assumption is false for INET 4.7's bridge.**
- The defect concerns the listener's address only. gPTP forwarding, per-copy correction, per-UE bearers and N = 1 equivalence are unaffected and exact.
- The misdirected frames are extra PCP 0 / PCP 5 data on the other UEs' DL between 0.109 s and 0.300 s. Their effect on gPTP timing in that interval has **not** been evaluated (stages 4+).

### 1.4 Options for your decision (none implemented)

1. **Static MAC entry for the listener only.**
   - The listener sits behind `dnEth`, which exists at initialisation, unlike the session ports. INET `MacForwardingTable` has an `object forwardingTable` parameter for static entries, e.g. `{address: <listener MAC>, vlan: 42, interface: "dnEth"}` on `upf.ethBridge.macTable`.
   - Configuration only.
   - Needs: a probe that the static entry is honoured with that interface name; an explicit listener MAC, since auto-assigned MACs depend on N (listener `0A-AA-00-00-00-02` at N = 1, `…03` at N = 2, `…05` at N = 4); and an amendment to design 3.3, which currently rejects static entries for session ports only.
2. **A listener "announcement" before 0.1 s.**
   - One VLAN-42 frame from the listener to the broadcast address, e.g. at 0.05 s. The bridge learns (42, listener) from it.
   - The broadcast is flooded to every session by definition. It would be counted separately, not as misdirected.
   - Configuration only. Changes the D-4 traffic.
3. **Keep D-4 as is and account for the window.** Report M_j, and require exact attribution of any gPTP timing effect of the misdirected frames in stages 4+. This changes the F0-4/F0-6 pass criterion, so it would need your explicit approval.

## 4. Deviations from design rev. 2 and caveats (for review)

1. **Learning recorders (config only, F0 census configs only).**
   - Design 3.3 said F0-6 would use the UPF PCAPs present in every run. Those are filtered to gPTP (`**.pcapRecorder[*].packetFilter = "Gptp* or TtPdelay* or injected*"`, from M2-S6), so they contain no data frame.
   - `M2S72-L` adds two UPF recorders: `ppp[0]` and `dnEth`, every packet, first 128 B.
   - **New row F0-9** shows they don't perturb the run: every output except theirs is identical to the `-norec` twin, with the log column `treeId` excluded (design X-1). The recorders create packet copies, which shifts the process-wide tree counter (10 732 to 83 766 cells; no other column differs). Fingerprints are identical.
2. **F0-6 is VLAN-aware** (keys (MAC, VID)), because that is the bridge's semantics. A MAC-only check would have passed the listener wrongly, on its untagged gPTP frames.
3. **F0-7.**
   - The delays are measured by following the eventlog's cause-event chain from each `MacForwardingTable` learn/lookup call back to the UPF interface event. The interface event's time equals the PCAP record's time; every key is matched one-to-one.
   - The fingerprint is obtained with `--fingerprint=0000-0000/tplx`: OMNeT++ prints the calculated value and exits normally. It is a command-line option on the F0 runs only.
4. **F0-5 gPTP SDU sizes** are as recorded: 62/92 B on DRB 1 under Q-0, and 61/91 B on DRB 4 under Q-d (UM). The classification is fail-safe: the count must equal the tunnel's gPTP copies, and these sizes must not appear on other DRBs. A first, uncommitted checker version used 62/92 for both and failed F0-5 under Q-d (UM). That was a checker error, found and corrected during development, before the committed checker and this record.
5. **The F0-1 cohort** is the GM messages whose transmission ended by T_end − 0.5 s. Later deliveries are reported (8 per DS-TT) and are not judged.
6. **T0 allowed differences** extend the design's "slave clockIdentity field" by the two derived quantities in §3.3: the FCS and the measurement layers' payload hash, plus one reconstructed end-of-run frame.
7. **Generator scope.**
   - N > 1 is generated only for the two idle sources (the F0 census).
   - The load app and the per-DS-TT TT-clock parameters (D-13) have no N > 1 translation yet. The generator refuses them, as the negative tests show. They belong to stages 4–5.
   - The generic DS-TT/talker vectorising rules refuse identity and address settings, so a new per-UE identity cannot be silently shared.
8. **Raw outputs are not committed** (1.0 GB). `raw-outputs.sha256` (sha256 `4199b4aa…`) holds the sha256 of each of the 2 310 PCAP and log files. `.sca` / `.vec` carry run dates and are not hashed, as in M2-S7.1.
