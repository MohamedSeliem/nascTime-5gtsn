### 2.1 Architectural decisions

| Decision | Reason |
|---|---|
| **No Simu5G change; no C++ or NED change.** NACK injection uses the upstream `IdealChannelModel` exactly as A2-V1 did; scheduler evidence uses the upstream `rtxAcid` log line. | Requirements 2, 5 and 6. **No architectural blocker:** both needs are met by configuration alone. |
| Hand-written `m2s72a2d.ini` that includes `m2s72s5.ini` unchanged, rather than a generator section | As `m2s72a2v.ini`. The generators and their outputs stay byte-identical, and the configuration is reviewable line by line. |
| The A2-V1 base (`M2S72-E0vN-q0-one0-n2-f1`) | Comparability with A2-V1-S1, the only genuine NACK record, and with the accepted N = 2 smoke |
| NACK injection on **every** UE | DR-07a demands NACK chains on more than one UE and multi-NACK groups. A multi-NACK group needs two UEs NACKing on the same process in the same TTI, impossible with A2-V1's single lossy UE. |
| `perDl = 0.3`: **a proposal (A2-D1)** | A2-V1's 0.1 gives a discard probability of 1e-4 per transport block (it recorded 0 discards). The value is a design parameter, not a prediction. The run decides the minima (protocol §2.1). |
| Loss draws on physical RNG 4, seed `400<repetition>` (the A2-V1 pattern) | Deterministic and identical in both twins: the twin differs only in logging (R-1). **Corrected in 162-R2 (§6.8):** RNG 4 is shared with the gNB's UL channel model and both UEs' DL error draws, so it is not an isolated stream. The earlier wording "own RNG 4 … no other module's draws change" was inaccurate. **Superseded in 162-R3 (§6.9):** P2 applied, per-UE RNG isolation (`ue[0]` DL → 4, `ue[1]` DL → 5, gNB → 6). |
| Twin comparison built on the **accepted** E0 comparator, plus a filtered console-log comparison | It reuses the reviewed non-perturbation rules, and adds the stronger check that every non-scheduler log line is equal |
| Evaluation with the **accepted** `check_m2s72_a21.py --contract full`, unchanged | The A-2.1 verdict is never re-implemented. The coverage check reads its record only. |
| Names refused by the WP-A1 and A3 tooling | A diagnostic can never be an E0v-N campaign run. Its counters live in their own record. |
| No runner; the protocol's commands plus `plan` | The run is V-6, an independent execution. No development-agent run path exists to misuse. |

### 6.8 Step 162-R2: RNG 4 mapping check

**Question (maintainer).** Does any instantiated random consumer other than the intended channel-error process share RNG 4?

**Answer: yes.** RNG 4 is shared, not isolated. Full evidence is in protocol §2.3. The accepted audit (`m2s72_rngaudit.py audit`, unchanged) gives the same map for the diagnostic and the twin. RNG 4 is mapped to:
- both UEs' `nrChannelModel[0]` (the intended DL error process; they share the stream);
- the gNB `channelModel[0]` (`IdealChannelModel`). It draws once per received UL transport block even at `per = 0` (`IdealChannelModel.cc:87–90`);
- both UEs' LTE-leg `channelModel[0]` (`StochasticChannelModel`). They are detached (`servingNodeId = 0`) and have no initialization draw (`insideBuilding = false`). So they are expected not to draw, but that is static evidence only.

No clock, MAC, scheduler or PHY is on RNG 4. A2-V1 had the identical mapping; its records and verdicts are unchanged.

**Assessment.**
- **Twin:** unaffected. The draws are the same in the same order in both, and logging draws nothing.
- **Diagnostic:** deterministic, and each attempt still fails with probability 0.3 marginally. But a UE's NACK realisation is coupled to the other UE's DL traffic and to all UL traffic. That does not affect a coverage-only diagnostic. It would affect any comparison of NACK realisations across configurations, which A2 does not make.

**Changes in 162-R2:**
- documentation and wording only: the ini header comment and the mixin description;
- protocol §2 / §2.2 / §2.3 and §3;
- this record (§2.1, §6.3);
- the `smoke-check` SM-2 text.

The resolved configuration is unchanged.

**Proposed, not applied:** P1 (UE DL models only on RNG 4; gNB on RNG 5) or P2 (per-UE RNGs 4 and 5; gNB on 6). Both were audited on a scratch ini (protocol §2.3). They are for the maintainer to decide before V-6.
