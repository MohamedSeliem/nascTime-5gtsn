## Research briefing

**1. What we learned**

- **The Q-d uplink starvation comes from unmodified upstream Simu5G v1.8.0.**
  - The installed sources equal tag `v1.8.0` (`1de882b`) file for file.
  - `LteSchedulerEnb.cc:403` comes from upstream commit `ef4ffa8e4` (2023, "Modify DRR scheduler").
- **Correcting that one line restores the missing grants.** With the line comparing the booked bytes against the pre-grant backlog (instead of the already-decremented `toServe`):
  - Q-d's UL becomes **identical to Q-0's**: 97 BSR reports, 7,866 grant TTIs, 57,009,090 granted bytes, 44.81 Mb/s achieved of 44.80 offered. The original build gave 2.48 Mb/s.
  - Q-d's DL and gPTP metrics are unchanged.
  - All 18 E0 gate rows pass on both candidate-build runs.
- **The one-line fix leaves the uncapped MaxCI scheduler (Q-0) unchanged.** On the candidate build Q-0 reproduces E0 in every PCAP, CSV, vector, scalar, MAC-log line and fingerprint. The only difference is one eventlog snapshot record holding a file offset (A.3).
- **The shared-TTI ambiguity in Q8 is resolvable from existing evidence.** The strict exclusion rule attributes every one of the 33 previously unexplained P1 HARQ-5 losses. In each case UE 0's PDUs of that TTI were all received, so the single deleted MAC PDU was UE 1's. It uses no logging order. The rule refuses each deliberately ambiguous or inconsistent case.

**2. Why it matters scientifically**

- **Configuration comparisons can be confounded by scheduler-implementation defects.** The E0 Q-d vs Q-0 uplink difference (18 ×) is not a property of QoS-aware scheduling or of the configuration. It is a grant-accounting defect that is exposed only by capped grants.
- Any Q-d result that depends on UL service is therefore **provisional on 1.8.0**. This covers UL residence, UL load interaction, cross-UE UL interference and listener-side UL counts. DL gPTP results of Q-d are unaffected at N = 1.
- **Reliability attribution at N > 1 can be kept packet-level and fail-closed** without new instrumentation, as long as the other UEs' PDUs in the TTI are positively shown as received. That is what makes HARQ-5 E2 / E1 runs evaluable by Q8.

**3. What remains unproven**

- **The counterfactual's declared success criterion was not met** (CF-1, CF-6). The evidence indicates check-definition errors. Accepting that requires your decision on a declared revision of those two checks; I have not re-run them under new definitions.
- **Generality of the fix:**
  - shown only for N = 1, factor 1, HARQ16, seed 0, one candidate line;
  - multi-codeword grants are not exercised;
  - the DRR scheduler, which introduced line 403, is untested;
  - whether later upstream revisions changed the line has not been fetched.
- **Q-d's DL** was unaffected here only because new DL SDUs re-activate the connection every TTI. A DL connection with backlog but no new arrivals is untested.
- **The attribution rule is validated on one N = 2 HARQ-5 run** (P1, UE 1, Q-0). Cases with d ≥ 2 deletions, or with several UEs all-missing in one TTI, are covered by the rule's logic but have not occurred in data.

### A.3 Diagnosis of the two failed rows (evidence; criteria not changed)

**CF-1.** I localised the eventlog difference read-only (`regression.txt`).
- After CF-1's filter, exactly **one** record differs: `S f 104864826 # 72664 t 0.36` vs `S f 104864804 …`. It is a snapshot record that holds a **file offset**.
- The two files differ in size by 22 B, because earlier records carry the run id (`<config>-0-<date>-<pid>`), which necessarily differs between runs.
- **0** event, message, module or log-text records differ.
- CF-1's comparator filtered the other index and snapshot record types but omitted `S`. That is a definition error in my check; the simulated behaviour is identical.

**CF-6.** The conservation parts hold. Only the declared bound failed.
- The UE queue at T_end, 516,161 B, is **exactly the original-build Q-0 value**: the UE accumulates about 0.5 MB between its BSR cycles of about 103 ms.
- I set the 0.5 MB bound without checking the Q-0 baseline. That was a calibration error in my prediction.

**Per the rules, both rows stay FAIL** and the verdict stays "NOT SUPPORTED as predicted". The evidence is preserved, and no further fix or re-definition was attempted.

**If you agree these are check-definition errors**, a declared revision would:
- (a) add `S` to CF-1's offset-record filter, or compare the event / message / module / log records only, as NONPERT does;
- (b) replace CF-6's absolute bound with "UE queue at T_end ≤ the original-build Q-0 value".

Both rows would then be re-evaluated on the **existing** candidate outputs, with no new run.

## Part B — strict shared-TTI attribution (`attr-p1.txt`; read-only on P1; opt-in `Q8(attr="exclusion")`)

**Rule E1–E5** (declared at `1231311`). The deletion in TTI t is attributed to UE k only if:

| # | Condition |
|---|---|
| E1 | The MAC log gives n DL MAC PDUs and d ≥ 1 deleted |
| E2 | The UEs with gNB RLC PDUs in t number exactly n |
| E3 | All reception windows are closed |
| E4 | Each candidate's PDUs of t are all received or all missing |
| E5 | The all-missing candidates are exactly d and include k |

E6 / E7 are the existing Q8 model rows. Logging order is not used.

**Result on P1 `M2S72-H-q0-Ca-n2` UE 1 (HARQ 5, real deletions):**
- **All 33** frames that were UNEXPLAINED under the revision-2 rule are attributed. Each TTI has n = 2, d = 1, candidates {UE 0, UE 1}; UE 0's PDUs are all received and UE 1's all missing. **0 unresolved.**
- The 5 frames already attributed (F6, F7, F18, F83, F89; n = 1) stay "lost", with the rule text added.
- No other fate changes.
- Q8 under the rule: **PASS**. 192 GM frames: 152 delivered, 38 lost (HARQ-process deletion), 2 censored. Pairs: 73 used, 22 lost, 1 censored. Replay: 37,308 deliveries predicted and observed. No destroyed SDU of any flow is left without an attributable discard; under the revision-2 rule there were 1,213.

## Part C — E2 design update (not run)

**Matrix (design approved in principle):**
- Candidate factors 0.8, 1.0, 1.1, 1.2, 1.3, 1.5 and 2.0 × L_tot, bracketed **separately per N ∈ {1, 2, 4, 8}, per placement (one0, sym) and per option (Q-0, Q-d)**.
- Ascending order; stop at the first factor overloaded by evidence (sustained growth on the load DRB together with achieved < offered), plus one factor above it.
- Then one or two bisection steps of the bracket, and replication of the two transition factors at seeds 0–2.
- One HARQ5 run per (N, option) at the last non-overloaded factor.
- The N = 1 capacity (≈ 1.21 × L_tot DL) is only a starting expectation for N = 1. It is never a threshold for N > 1.
- Size: at most about 270 runs, usually fewer because of the stop rule.

**Q8 at N > 1.** HARQ5 runs use the strict exclusion rule (Part B), declared in the E2 protocol. Unresolvable TTIs fail Q8. That is a stop condition, not a reclassification.

**Effect of the Q-d UL issue on comparability:**

| Result class on Simu5G 1.8.0 | Status |
|---|---|
| DL gPTP timing, delivery and Q8 for Q-d and Q-0 | Comparable. DL is unaffected at N = 1 (identical with and without the candidate fix) |
| DL capacity / saturation of Q-d | Comparable at N = 1. At N > 1, **provisional**: QoS-aware DL quotas are capped per node, and a backlogged DL connection without new arrivals could be deactivated by the same line (untested) |
| Any Q-d UL quantity (UL throughput, UL backlog, UL timing, listener UL counts), and any Q-d vs Q-0 comparison involving UL load or UL-induced interference (NW-TT and listener link sharing, Pdelay on shared links) | **Provisional / not comparable.** Q-d UL is starved by the 1.8.0 defect. Q-d runs carry 1/18 of Q-0's UL load at the same offered load |
| Q-0 (MaxCI) results | Unaffected by the defect: the fix leaves uncapped MaxCI scheduling unchanged (CF-1 evidence) |

**Options for E2 (your decision).**
1. Run Q-d on 1.8.0 with UL load = 0 and label it "DL-only comparison". This removes the confound by design.
2. Run Q-d with UL load and label every Q-d UL-dependent result provisional on 1.8.0.
3. Pursue the fix as an upstream contribution, and adopt it only through a future official release as a new baseline (contribution-plan rule). Results on a patched build stay counterfactual evidence only.
