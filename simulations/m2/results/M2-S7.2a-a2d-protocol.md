### 2.1 The declared diagnostic configuration (decision A2-D1)

**A2-D1 is provisionally approved (maintainer, step 162-R1).** The approval covers:
- `perDl = 0.3` on every UE;
- `harqReduction = 1`;
- the N = 2 base derived from A2-V1 (`M2S72-E0vN-q0-one0-n2-f1`).

**RNG streams (maintainer, step 162-R3): P2, per-UE RNG isolation, is approved as part of A2-D1:**
- `ue[0]` DL channel-error process → RNG 4;
- `ue[1]` DL channel-error process → RNG 5;
- gNB channel model → RNG 6.

`perDl`, `harqReduction`, the N = 2 base and the logging-only twin difference are retained.

These form the declared A2 diagnostic configuration. **The approval is of the configuration design only:** it is not an authorisation of V-6, not a result, and not a scientific acceptance.

The text below gives the design rationale as written before the approval.

**`perDl = 0.3` on every UE, `harqReduction = 1`.** A2-V1 used 0.1 on `ue[1]` only, and recorded 0 discards and no multi-NACK group (S1 closure §5).

**Sizing rationale. These are probabilities of the declared mechanism, not predictions of counts:**
- With independent attempts, a transport block is discarded with probability `perDl^(maxHarqRtx + 1) = perDl^4`. At 0.1 that is 1e-4; at 0.3 it is 8.1e-3.
- Two UEs both NACK a same-TTI pair with probability `perDl^2`. That is 0.01 at 0.1 and 0.09 at 0.3, and it is 0 when one UE is loss-free, as in A2-V1.

**Whether the minima are met is decided only by the run (§4).** A run that misses one is **not a valid diagnostic**: it is never extrapolated. A changed parameter is a new declaration and a new decision.

#### 2.3.1 History: the shared RNG 4 found in step 162-R2 (configuration up to `a53a606`; superseded)

The text below is kept as written in 162-R2. It describes the mapping before P2, which was the A2-V1 pattern. A2-V1 (`m2s72a2v.ini`) keeps that mapping unchanged, with its records and verdicts.

**Question.** The NACK mixin maps channel-model local RNG 0 to physical RNG 4. Is any other instantiated random consumer on RNG 4?

**Method.**
- The accepted RNG audit (`check/m2s72_rngaudit.py audit`, S5-2, unchanged) on the diagnostic, the twin and the base, from the effective entries resolved by OMNeT++ 6.5.0.
- The constructed module types (SM-3, eventlog).
- Source reading of upstream Simu5G 1.8.1.

**Effective mapping, N = 2.** The same in the diagnostic and the twin:

| Module | Constructed type | Physical RNG | Matching entry | Draws on RNG 4 |
|---|---|---|---|---|
| `ue[0].cellularNic.nrChannelModel[0]` | `IdealChannelModel` | 4 | `**.nrChannelModel[*].rng-0 = 4` | Yes: one `uniform` per received DL transport block (the intended DL error process) |
| `ue[1].cellularNic.nrChannelModel[0]` | `IdealChannelModel` | 4 | `**.nrChannelModel[*].rng-0 = 4` | Yes: the same, for `ue[1]` |
| `gnb1.cellularNic.channelModel[0]` | `IdealChannelModel` | 4 | `**.channelModel[*].rng-0 = 4` | **Yes.** `IdealChannelModel::isReceptionSuccessful` (`IdealChannelModel.cc:87–90`) calls `uniform(0.0, 1.0)` for every received frame, even with `per = 0`. So every UL transport block of either UE draws from RNG 4. |
| `ue[0]`, `ue[1]` `cellularNic.channelModel[0]` (LTE leg) | `StochasticChannelModel` | 4 | `**.channelModel[*].rng-0 = 4` | Expected none, from static evidence only. `insideBuilding = false`, so there is no draw at initialization (`StochasticChannelModel.cc:74–75`). The LTE leg is detached (`*.ue[*].servingNodeId = 0`, `nrServingNodeId = 1`), so it receives no frames. No draw count was observed. |

No clock, MAC, scheduler or PHY is on RNG 4:
- the clocks are on RNG 1 and 2 (audit RA-2 PASS);
- the MAC, PHY, scheduler tie-breaks and BLER table are on RNG 0;
- `IdealChannelModel::getSIR` / `getSINR` draw nothing.

The audit's RA-3 line reads "physical RNGs drawn by modules of >= 2 UEs: {0: [0, 1], 4: [0, 1]}". A2-V1 (`m2s72a2v.ini`, unchanged) used the identical two `rng-0` entries. Its RNG 4 was shared the same way, including by `ue[0]`'s loss-free DL model, which also draws. This note does not change any A2-V1 record or verdict.

**Shared, not isolated.**
- *Isolation* would mean that the DL error process of a UE is the only consumer of its stream. Its realisation would then be a function of that UE's own DL attempt sequence alone.
- Here the k-th RNG-4 draw goes to whichever channel model receives the k-th frame. So a UE's NACK realisation depends on the interleaving of its own DL receptions with the other UE's DL receptions and with all UL receptions at the gNB.
- Each draw is still a U(0, 1) sample from the one Mersenne Twister stream. So each attempt still fails with probability 0.3 marginally, and the run is deterministic and reproducible per repetition.

**Effect on the twin comparison: none.**
- The twin and the diagnostic resolve to identical entries except the scheduler log level (R-1).
- Logging consumes no random number.
- So both runs make the same draws in the same order, and T-1 … T-3 compare like with like.
- Any divergence would itself be a non-perturbation failure, which T-1 / T-2 detect. The sharing cannot mask one.

**Effect on the diagnostic: none on its stated purpose.**
- The diagnostic is a coverage diagnostic. Its minima (§4) are counted from the realised run. No result is compared across configurations, N, seeds or with A2-V1 on the basis of matching NACK realisations.
- The coupling would matter if anyone did make such a comparison. For example: "the same NACK pattern as A2-V1", or a run whose UL traffic differs while expecting the same DL NACK sequence. Such a comparison is **not** supported by this configuration, with or without a correction.
- The declared description "loss process on its own RNG 4" was inaccurate, and has been corrected in `m2s72a2d.ini`. The resolved values are unchanged.

**Smallest correction, as proposed in 162-R2.** (P2 was approved and applied in 162-R3; see above.) Both variants were checked with the accepted audit on a scratch ini (not committed):

| Variant | Replace the two `rng-0` lines with | RNG 4 consumers | RA-3 (UEs sharing a stream) |
|---|---|---|---|
| **P1** (smallest) | `*.ue[*].cellularNic.nrChannelModel[*].rng-0 = 4`, `*.gnb1.cellularNic.channelModel[*].rng-0 = 5`, `num-rngs = 6`, `seed-5-mt = 500${repetition}` | Only the two UEs' DL error models. gNB UL → RNG 5. LTE leg back to its base mapping (RNG 0). | `{0: [0, 1], 4: [0, 1]}`: the two UEs still share RNG 4 |
| **P2** (per-UE isolation) | `*.ue[0]…nrChannelModel[*].rng-0 = 4`, `*.ue[1]…rng-0 = 5`, `*.gnb1.cellularNic.channelModel[*].rng-0 = 6`, `num-rngs = 7`, seeds 5 and 6 | Only `ue[0]`'s DL error model. RNG 5 only `ue[1]`'s; RNG 6 only the gNB's. | `{0: [0, 1]}`: only the base's existing RNG-0 sharing, which is unchanged and not a channel-error consumer |

Either variant:
- keeps every probability, type and other entry;
- keeps the twin identical except for logging;
- RA-1 / RA-2 PASS (no auto-seeded consumer, no clock collision at N = 2).

Applying one would also change:
- the `NACK` constant of `m2s72_a2d.py` and its tests;
- the R-2 count;
- `runconfig-*.txt` and `smoke-init.json` (re-recorded);
- the R-3 difference list against A2-V1, which gains the RNG entries.

The trade-off is that the diagnostic then departs from the A2-V1 RNG pattern. Recommendation: no correction is needed for the coverage purpose. If the maintainer prefers exclusive streams, P1 is the minimal change and P2 gives true per-UE isolation. The decision is the maintainer's, before V-6.

## 6. Procedure for the independent executor (V-6; after authorisation only)

1. Environment D-2:
   - OMNeT++ 6.5.0 / INET 4.7.0 / unmodified Simu5G 1.8.1 (`7477d266`), release builds;
   - `src/nasctime/m2/build.sh` at the authorised commit;
   - a fresh results root; the same binaries for both runs.
2. Resolution (no simulation):

   ```bash
   python3 -B check/m2s72_a2d.py resolve <records>/resolution -- <opp_run prefix>
   ```

   It must report AS DECLARED, and the outputs must equal the committed `results/M2-S7.2a-a2d/runconfig-*.txt` on their effective entries. The RNG streams are then checked on the executor's own resolution together with the committed smoke record, or the executor's own re-run of `smoke`:

   ```bash
   python3 -B check/m2s72_a2d.py rng-check <records>/resolution/runconfig-<diag>.txt <records>/resolution/runconfig-<twin>.txt results/M2-S7.2a-a2d/smoke-init.json
   ```

   It must report AS DECLARED.
3. The commands of:

   ```bash
   python3 -B check/m2s72_a2d.py plan <nascTime> <simu5g> <inet> <root>
   ```

   in this order:
   1. the diagnostic, then the twin, each with its manifest;
   2. `twin`;
   3. `check_m2s72_a21.py a21 … --contract full`;
   4. `coverage`;
   5. manifest re-verification.

**Stop and keep everything:**
- on any non-zero simulation exit;
- on an evaluation error;
- on twin NOT SHOWN;
- on NOT A VALID DIAGNOSTIC.

Never rerun into the same root. Nothing is deleted.

**Acceptance (V-6):** the maintainer reviews the twin record, the coverage record and the A-2.1 record. Only then may the full-contract status of a configuration be decided. A2-V1's historical verdict is not reopened by V-6.
